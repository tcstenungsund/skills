# Build Instruction: School Skills Gallery (SKILL.md Repository + Generated Teacher Portal)

## What to build

A GitHub repository that serves as the canonical source of truth for an organization's **Agent Skills** (SKILL.md format), plus a GitHub Actions workflow that automatically generates a **static HTML gallery site** (deployed via GitHub Pages) for non-technical end users — schoolteachers using consumer AI services (claude.ai, gemini.google.com, chatgpt.com, Microsoft 365 Copilot Chat).

Teachers never touch git, GitHub, markdown, or the repository. Their entire interface is the generated website: browse skills, read what it does, see the version and date, and get the skill into their AI tool with one click.

The repository is maintained by one or two technically comfortable people via pull requests. All teacher-facing content is in **Swedish**. Repository-internal content (scripts, workflow files, maintainer README) may be in English.

---

## Audience and problem statement (context for the LLM)

- ~Dozens of teachers, no programming background, no git knowledge. Assume zero tolerance for jargon in anything they see.
- Teachers use *different* AI services and different account tiers (free and paid). No common platform can be assumed. Distribution must be pull-based via a website, never push-based via admin tooling (we do not control the services' admin planes).
- Shared problems the skills solve: writing tests, grading tests against grading criteria (*kunskapskrav*), creating assignments, applying the school's graphical profile, etc.
- Critical failure mode to design against: **version drift**. Skills pasted into Gem/GPT-style containers do NOT update when the source updates. Teachers will be stuck with stale copies forever unless the site makes the version visible and stale copies easy to identify and replace.
- Critical content-integrity rule: the SKILL.md repo is the ONLY place where a skill is authored or edited. Never author or "fix" a skill inside a Gem, custom GPT, Copilot instruction field, or chat. Everything is exported *from* the repo; nothing is edited *in* the destination.

## Repository structure

```
school-skills/                        # repo root (name to be decided by org)
├── skills/                           # one folder per skill — the source of truth
│   ├── create-prov/
│   │   ├── SKILL.md                 # required, YAML frontmatter + body
│   │   ├── references/              # optional, ONE level deep only
│   │   │   ├── kunskapskrav-gy25.md
│   │   │   └── grafisk-profil.md
│   │   └── assets/                  # optional downloads (PDFs, images, templates)
│   │       └── mall-prov.docx
│   └── bedomning/                   # second skill, same layout
│       └── SKILL.md
├── site/                            # generated by the Action — DO NOT hand-edit
│   ├── index.html
│   ├── skills/<slug>/index.html     # one page per skill
│   ├── downloads/                   # zips, reference bundles
│   └── instruktioner/<slug>.txt     # paste-block variants (plain text)
├── docs/                            # maintainer documentation
│   ├── ny-skill.md                  # how to add a skill (Swedish — may be read by
│   │                                # semi-technical colleagues)
│   └── CHECKLIST.md                 # pre-merge review checklist
├── scripts/
│   └── build_site.py                # site generator (stdlib only — no dependencies)
└── .github/workflows/
    └── build.yml                    # builds site + downloads, deploys Pages
```

Rules the builder must enforce/document:

- Skill folder names: **lowercase kebab-case only**. No spaces, no underscores, no capitals. (Required by the Agent Skills standard/consumers.)
- `SKILL.md` must exist, exact capitalization, at the root of each skill folder.
- **No README.md inside a skill folder** — all documentation lives in SKILL.md. A repo-level README for maintainers is fine.
- SKILL.md body under **500 lines**; split into `references/` files when approaching the limit.
- Reference files must be **exactly one level deep**: SKILL.md links directly to `references/foo.md`; no chains where a reference points to another reference. Reason: AI agents may partially-read chained files and never reach the payload.
- The Action must **fail the build** on violations of any of the above (folder naming, missing SKILL.md, >1-deep reference chains). Bad metadata should never silently publish.

## SKILL.md frontmatter schema

Use the open Agent Skills standard fields plus a small governed extension. All skills must carry:

```yaml
---
name: create-prov                  # must equal folder name; kebab-case
description: >-                    # ALWAYS-loaded by agents; must contain trigger phrases
  Skapar prov och kursprov utifrån ämne, kurs och kunskapskrav.
  Använd när användaren vill skapa ett prov, kursprov eller
  salstentamen enligt Gy25.
version: 1.2.0                     # semver; bump on every change
updated: 2026-11-07                # ISO date of last substantive change
owner: Kenneth Frantzen            # accountable maintainer, a human's name
---
```

Notes for the builder:

- `name` and `description` are the standard fields every consumer reads. `description` is loaded at every session start (~100 tokens each) — keep it under ~150 words and pack it with "use when…" trigger phrases, since that string is what decides whether the skill fires.
- `version`, `updated`, `owner` are our organizational extensions; the site generator reads them. Validate their presence in the build.
- Versioning discipline: patch = typo/small fix; minor = added content; major = behaviour change or removal. Script arguments, file names, and SKILL.md structure must NOT change in patch versions — downstream paste-block consumers keep working.
- Recommend also a lightweight `CHANGELOG` section at the bottom of each SKILL.md body (date + one line per change). Cheap, and it surfaces on the skill page.

## The three export formats (generated by the Action)

The generator produces exactly three export artifacts per skill. Do not invent per-platform variants of the instruction text — one paste-block serves Gemini, ChatGPT, and Copilot alike; per-platform copies would drift apart within a term.

### 1. Skill ZIP (for Claude users, and any consumer of the open standard)

- Zip the whole skill folder so it unpacks as `create-prov/SKILL.md` (+ subfolders). The folder-in-zip layout matters; a bare SKILL.md at zip root is not always accepted.
- claude.ai upload path: Settings → Capabilities → Skills → Upload. Works on free plans too, so do not assume paid accounts.
- Regenerated on every build so the download is always current.

### 2. Paste-block (universal fallback — the MOST USED export in this org)

- Plain-text rendering of the SKILL.md body with:
  - YAML frontmatter stripped;
  - markdown heading syntax kept readable (it reads fine as text);
  - **relative links to reference files rewritten or annotated** — GOTCHA: a pasted instruction saying "see references/kunskapskrav.md" points nowhere once pasted into a chat window. Either inline the reference content, or append a footer line like `Bifoga de nedladdade filerna från webbplatsen om instruktionen hänvisar till dem.` Decide per-skill at authoring time; the generator must at minimum detect dangling relative links and warn.
- Served at a stable plain-text URL (`/instruktioner/<slug>.txt`) AND via a copy-to-clipboard button on the skill page.
- Size ceiling: keep the paste-block under ~10,000 characters where possible. Microsoft Copilot's custom-instruction field is documented at ~20 KB (their Copilot Cowork figure) and consumer attention spans are shorter than that. Long context belongs in `references/` files, not in the instruction body.
- Platform-specific consumption (document on the site, not in the export):
  - **Gemini**: Gem Manager → New Gem → paste into instructions → upload reference files as knowledge files.
  - **ChatGPT**: paste into a Project's instructions field (note: custom GPTs are being retired December 11, 2026; do not build anything GPT-specific — paste-block covers Projects and incoming skill-format features).
  - **Microsoft Copilot Chat**: Settings → Personalization → Custom instructions. NOTE: Copilot has a *single global* instruction box per user — a teacher pasting three skills will concatenate them. Document this and instruct: one skill per Copilot user, or curate a combined "School Master" skill specifically for Copilot users.

### 3. Reference/asset bundle (per skill, if present)

- Everything in `references/` and `assets/` offered as individual downloads (and/or one zip).
- These are the files teachers upload into the Gem/GPT/Copilot knowledge-file slots. Instructions go in the paste-box; context documents go in the attachment slot. Keep that separation visible on the page: "Text att klistra in" vs "Filer att ladda upp".

## The generated website (GitHub Pages)

Requirements:

- **Static HTML only**, generated by `scripts/build_site.py` (Python stdlib only: pathlib, yaml is NOT stdlib — either vendor a minimal frontmatter parser or use a simple regex parser for the limited schema; keep zero pip installs to make the Action bulletproof).
- Site language: Swedish. No English UI labels.
- Visual style: use the school's graphical profile if colors/logo are supplied (accept a `site-theme.json` with brand colors + logo path); otherwise clean, accessible defaults. WCAG AA contrast is mandatory — teachers include screen-reader and low-vision users.
- Mobile-friendly: teachers will open this on phones during fika.
- **index.html**: one card/table row per skill showing: name (Swedish display name — see below), one-line description, version, updated date, owner. Sortable/filterable is nice-to-have; simple, always-visible list is the requirement. No search infrastructure — this is a dozen skills, not a thousand.
- **Per-skill page** must show, in order of visual priority:
  1. Display name, version badge, updated date, owner (a face and a date make stale copies discoverable; "ask Anna if confused" is the support model)
  2. "Vad den gör" — plain-language explanation
  3. **"Kopiera instruktionen"** copy-to-clipboard button (primary CTA)
  4. Per-platform short instructions with headings: *I Claude*, *I Gemini*, *I ChatGPT*, *I Copilot* — 3–5 numbered steps each. Screenshots live in `docs/screenshots/` and maintainers add them over time; the page must degrade gracefully when a screenshot is missing.
  5. ZIP download ("Ladda ner för Claude")
  6. Reference file downloads
  7. Changelog/history
- Include a prominent line on every skill page: `Nuvarande version: 1.2.0 (2026-11-07)` — the whole anti-drift strategy rests on this being unmissable.
- A `version-history` block per skill listing the changelog entries.

Gotcha — visibility of the Pages site: GitHub Pages on a **private repo requires a paid plan**. Decide before building:
- Option A: public repo (acceptable if content is non-sensitive: general pedagogy, graphical profile, rubrics — no pupil data, ever). Cheapest and simplest.
- Option B: private repo + paid plan org.
- Option C: generate the site artifact but host it internally (school intranet/webserver).
Enforce: **no pupil-identifying data or exam answer keys in any skill**, regardless of option. A pre-build grep check for common pitfalls is a sensible extra validation the generator can perform (fail build on obviously sensitive paths like `svar`, `facit`, national ID patterns — implement as a warn list, maintainer-overrideable).

## The GitHub Action (`build.yml`)

- Trigger: push to `main` affecting `skills/**`, plus manual dispatch.
- Checkout with `fetch-depth: 0` — GOTCHA: skill dates should come from git history (`git log -1 --format=%cs -- <skill dir>`), and shallow checkout makes every date "today". Alternatively rely on the frontmatter `updated` field and validate it was bumped — safer against rebases; pick one (recommend frontmatter `updated` as canonical, git date as validation warning).
- Steps: validate (schema, naming, depth, dangling links) → build site + zips + paste-blocks → deploy Pages (use the official `actions/configure-pages` + `actions/deploy-pages` pair; the legacy `peaceiris/actions-gh-pages` deploy-to-branch is deprecated behaviour — keep main-to-Pages-deployment).
- Validation failures must fail loudly with readable error messages naming the offending skill folder — a maintainer (who is *not* a programmer) must be able to act on the message without decoding stack traces.
- Pin action versions; no third-party actions beyond the official `actions/*` set. Zero network dependencies beyond the runner.
- The `site/` directory is generated; add a line to the maintainer README forbidding manual edits (consider not even committing `site/`, letting Pages deploy the artifact directly).

## Governance model (document in docs/, surface partially on the site)

- One named owner per skill; owners are accountable for updates and answers.
- All changes via pull request. For a maintainer-team of two, branch protection is light, but the PR pattern still enforces the "nothing edited in destination tools" rule and gives rollback.
- Skill lifecycle: draft in a personal sandbox → PR to `skills/` → reviewed → published on next merge. Deprecation: move skill folder to `skills/_arkiv/` (generator skips underscore-prefixed folders) rather than deletion — teachers may still be mid-term on a removed skill and need the old version discoverable.
- Update cadence expectation: check each skill's `updated` date at the start of each term. The site index should visually flag skills not touched in >6 months ("kan behöva ses över").
- License/internal-use notice in the footer: internal use only, CC BY-SA for original instructional content (adapt to org policy).

## Acceptance checklist (verify all before delivery)

1. Adding a new `skills/<kebab-case>/SKILL.md` with valid frontmatter and pushing to `main` results, within one Action run, in: a new skill page, an index entry, a downloadable zip, a `.txt` paste-block, and downloadable reference files.
2. A skill with invalid frontmatter (missing `version`, mismatched `name`, camelCase folder) fails the build with a readable error message identifying the folder and the rule violated.
3. Frontmatter-relative links in the paste-block are either resolved (inlined) or flagged; no silent dead pointers.
4. The copy-to-clipboard button works on mobile Safari and Chrome (use the async Clipboard API with a fallback to `document.execCommand('copy')`; GOTCHA: clipboard APIs require HTTPS and a user gesture — GitHub Pages provides HTTPS, the button handler must be inside the click listener, not pre-executed).
5. Page and downloads show identical version numbers, derived from one source (frontmatter).
6. The site renders correctly with JavaScript disabled except that copy buttons degrade to "select all in the textarea" (progressive enhancement — no framework required; hand-rolled HTML with a few lines of vanilla JS is the right amount of engineering here).
7. No student data paths, answer keys, or secrets can end up deployed (grep validation present and tested).
8. Deleting/renaming a skill does not break Pages (old URLs should 404 cleanly, not crash the generator; consider a generator-emitted redirect stub or leave dead links to teach staleness — choose the former).

## Reasoning recap — why it is shaped this way (include in maintainer docs)

- **Git repo as backend, website as frontend**: the repo gives versioning, review, rollback, and a single source of truth; the website gives teachers a zero-threshold consumption path. Neither alone solves both problems.
- **SKILL.md canonical despite heterogeneous consumers**: Agent Skills is an open standard (published as such by Anthropic, adopted by other agents, and ChatGPT custom GPTs are migrating to a skills-based plugin model with GPT retirement announced for December 11, 2026). Authoring in the open format means being import-ready for every converging platform while serving non-Claude users today via the paste-block.
- **Exactly three exports, no per-platform instruction variants**: platform-specific text forks drift; a single paste-block plus platform-specific *installation tutorials* (on the page, with screenshots) achieves the same result with one source of truth.
- **Anti-drift measures as the real product**: version stamps, updated dates, named owners, staleness flags, changelogs. The formats are trivial; preventing eleven divergent copies of the grading rubric by spring term is the actual mission.
